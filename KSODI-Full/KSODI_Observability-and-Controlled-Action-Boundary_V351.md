## 1. Why the boundary matters

KSODI produces structured observations about attributable events,
source-local trajectories and, where separately admitted, relational patterns.
An observation may inform a later governed decision. It does not become an
instruction merely because it is numeric, unusual, aggregated, outside a
declared corridor or presented as an alert.

The earlier label "From Observability to Controlled Action" could be read as a
method-internal transition or guaranteed progression. The v3.50 and v3.51
boundary is stricter: observation and controlled action are separated by
purpose, evidence, governance, authority and an independently declared
Controller or human decision.

```text
observable events
  -> attributable Observer records
  -> deterministic calculations and typed findings
  -> governed interpretation / policy check
  -> separate authorized Controller or human decision
  -> permitted action or explicit no-action
  -> new attributable events available for later observation
```

The return path creates new evidence. It does not prove that the decision was
correct, that KSODI caused an improvement or that the earlier observation was
complete.

## 2. Four distinguishable spaces

v3.51 makes the spatial and authority boundary explicit:

| Space | Bounded role | Principal guard |
| --- | --- | --- |
| participant processing/library/archive space | entity-specific processing or retained material under the applicable system description | not automatically visible to an external Observer |
| transient interaction/work space | bounded availability of externalized contributions, signals and tool outputs | shared availability does not merge identities, archives, understanding or responsibility |
| Observer-side Hangar | qualified retention, comparison and reconstruction view over typed observation objects | contains observation objects, not private inner states or action permission |
| Controller/action space | separately authorized decision, intervention or execution space | never activated by a score, display, alert or Hangar view alone |

An observable interaction event requires an attributable signal, event or
retained state change entering a declared relational observation space.
Reconstructible communication, understanding, mutual understanding,
agreement, resonance and causal influence remain further questions.

The currently published [KSODI Hangar](../KSODI-Hangar_V351.md) provides the
broader Hangar orientation. This file governs only the Observer-to-action
separation; its four-space distinction is explicit here and does not depend on
using a Hangar metaphor.

## 3. Responsibility and authority map

| Component or role | May do | Must not be inferred |
| --- | --- | --- |
| KSODI Observer | emit typed, attributable method results and diagnostics under declared profiles | decision, command, intervention, truth, intent or desirability |
| deterministic view/calculation consumer | calculate declared transformations over valid retained operands | authority to change method identity, profile or observed environment |
| assistive evaluating model | receive a bounded attributable context package and propose an interpretation or question | replacement of the deterministic result, autonomous decision or hidden-state access |
| human-facing governance view | present rounded or simplified navigation with drill-down | that the display is the stored result, a later operand or a target to optimize |
| governance policy | define permissible uses, evidence requirements, corridors, escalation paths and accountable roles | that a KSODI value alone supplies the policy |
| Controller | validate an authorized input envelope and select a permitted response or no-action | that it is part of a KSODI formula or entitled to rewrite Observer evidence |
| human or executing system | approve or perform an authorized action and record the outcome | that execution validates the observation, policy or action |

Human responsibility is not removed by automation. A deployment must state
who owns profile choice, policy approval, Controller behavior, exception
handling, audit review, override and shutdown authority.

## 4. What the current layers contribute

KSODI-Light is a human-facing orientation space using disclosed working
questions and optional `0..5` values. Prompt-level reflection or a participant
choosing a different continuation is not a system-level Controller contract.

KSODI-Standard-Eval is the formal monadic line:

```text
K/S/O/D/I -> typed Z_A(k_A) -> monadic IK views
```

Its formal numeric results use `[0,1]` under declared profiles. Light values
and formal values are not direct rescalings. A complete typed `Z`, `IK_w`,
`IK_M2`, `IK_ref`, `AxisDev_ref` and their joint evaluation view answer
different declared questions. None is a command, total truth or universal
quality score.

KSODI-Full begins with separately declared relational observation. `R0`
receives distinguishable source-local movements plus explicit pairing or
constellation identity. Its numeric result and categorical gate state remain
separate:

```text
valid numeric R0 at/above the declared threshold -> open
valid numeric R0 below the declared threshold    -> closed
non-numeric R0                                   -> not_evaluable
incomparable or invalid input                     -> no valid R0 result
```

An open `R0` gate means only that one declared eligibility contract admits a
compatible downstream calculation. It is not permission to act and not proof
of relation, coupling, resonance, agreement, alignment or success.

Current primary dyadic `IK_rel` additionally requires its exact compatible
open numeric canonical-complete dyadic `R0` handoff. Reduced or n-adic gates
do not silently open that branch. Later `R_geom`, `R_pace`, voice/signal-media
or other R-family branches remain separately staged unless their own versioned
contracts say otherwise.

The published Phase-H v3.51 review makes the declared R₀/IK_rel behavior,
expected profile sensitivity and scalar projection loss visible across 52
synthetic reference rows. Its generator checks declared fixture expectations;
it does not independently exclude a contract contradiction. No finding
supplies an action signal: complete retained operands, typed statuses, profile
identities and the reverse route remain necessary, and a passing fixture run
does not create runtime-conformance or Controller authority.

## 5. Observer outputs remain observations

The following may be reportable under their own contracts:

- a typed numeric or non-numeric operator, Z, IK, R0 or IK_rel result;
- a comparable source-local first or second difference;
- a numeric R0 result with an open or closed gate state;
- a window with exact membership, coverage and status partitions;
- a gate-open rate, movement-band rate or another valid positive-denominator statistic;
- a qualified Hangar distribution or point-cloud view;
- a governed corridor departure, alert or other separately defined diagnostic.

None independently selects an action. In particular:

- numeric zero is not a substitute for missing, inapplicable, failed or incomparable evidence;
- a closed or non-evaluable R0 gate does not automatically pause a system;
- an open R0 gate does not authorize calculation beyond the exact compatible branch and does not authorize intervention;
- a high or low IK, R0 or IK_rel value does not establish correctness, desirability, safety, truth or intent;
- a window or aggregate does not inherit the identity or authority of a participant event;
- a sparse high numeric subset does not become the whole opportunity window;
- PPWA or another partition-preserving future view does not relax v3.51 identity, validity or authority requirements;
- `legacy_reconstructible`, `legacy_partially_reconstructible` and `reconstruction_pending` do not authorize fabricated provenance or action.

## 6. Raw result, display and assistive interpretation

v3.51 separates at least:

```text
retained operands and provenance
  -> raw typed result
  -> numeric policy / transformation
  -> machine calculation value
  -> rounded display value and rendered mark
```

The unrounded result remains authoritative for its declared calculation. A
display value is never fed back as though it were the retained operand. Every
human-facing view keeps a practical route to identities, profiles, window
members, status partitions, transformations and evidence.

An assistive LLM may receive a bounded, attributable package to help a human
interpret patterns or formulate follow-up questions. Its output remains a
separate interpretation record. It cannot overwrite the deterministic result,
invent missing evidence, silently change a profile or authorize action.

The display is an instrument for navigation, not the target communication
must satisfy. Alerts and corridors open diagnostic questions. They do not
declare defects or prescribe interventions.

## 7. Minimum controlled-action envelope

A Controller-facing integration should receive an explicit envelope rather
than an unlabelled score or visualization:

```text
ControlledActionInput {
  observer_record_ids
  method_result_and_view_ids
  method_profile_policy_and_code_versions
  source_event_trajectory_pairing_and_window_scope
  raw_result_statuses_values_and_component_masks
  numeric_policy_and_transformation_provenance
  comparability_coverage_and_status_partitions
  uncertainty_and_reconstruction_references
  assistive_interpretation_reference_if_used
  policy_id_and_version
  authorized_controller_id
  permitted_action_set
  human_approval_requirement
  freshness_and_expiry
  provenance_and_audit_reference
}
```

Rounded display values and rendered marks are not Controller operands. Before
any action, the Controller validates identity, policy authority, profile
compatibility, evidence freshness, coverage, permitted action set and required
human approval. Invalid, stale, incomparable or unauthorized input does not
become a default KSODI action. Logging, clarification or human review may be
required by an external policy; that response is not produced by a KSODI
formula.

## 8. Bounded customer-support example

Suppose an external Observer reports a source-attributed sequence with
declining numeric coverage and several `not_observable` operator results. The
Observer records those facts, profiles, status reasons and evidence routes. It
does not conclude that the agent is wrong or select a remedy.

A separately approved support policy might require a human review when the
evidence envelope satisfies its own conditions. An authorized Controller may
then create a review task. The reviewer may request missing order evidence,
clarify the desired outcome, continue without intervention or select another
permitted response.

Any subsequent interaction is evaluated as new attributable evidence. A later
change in KSODI values does not by itself prove that the intervention caused
the change or that the outcome was beneficial.

## 9. Feedback and anti-circularity controls

When Observer outputs can influence the observed system, preserve:

- separate Observer, assistive-model, Controller and human identities and logs;
- the exact policy and evidence envelope used for each decision;
- attributable records for Controller commands and system responses;
- delay, cooldown and rate-limit policies outside method formulas;
- protection against a Controller rewriting the evidence it consumed;
- protection against an Observer redefining its own profiles, thresholds or evidence basis through an undeclared feedback loop;
- explicit evaluation of feedback effects as new observations;
- independent human override, audit and shutdown paths where required.

Without this separation, a system may optimize against its own Observer,
confuse intervention effects with organic trajectory movement, convert a
display into the optimization target or create an unreviewable feedback loop.

## 10. Implementation and conformance questions

A v3.51 implementation-boundary review asks at least:

1. Are Observer records, assistive interpretations, governance approvals, Controller decisions and executed actions distinct event types?
2. Can every displayed or machine-consumed result return to exact retained operands, identities, profiles, statuses, windows and transformations?
3. Are non-numeric and incomparable states preserved rather than converted to zero or a default action?
4. Are alerts, corridors and rankings labelled as observations or policy inputs rather than commands?
5. Can a Controller act only through a separately versioned policy and authorized input envelope?
6. Are profile changes, threshold changes and feedback effects themselves attributable and auditable?
7. Can the system fail closed at the Controller boundary without rewriting the underlying observation?
8. Can human reviewers inspect uncertainty, excluded partitions and missing evidence before action?

A passing documentation review is not runtime conformance. Runtime evidence,
integration tests and domain validation remain separately required.

## 11. Non-claims and release boundary

This note does not claim that:

- autonomous systems always require a complete KSODI Observer;
- KSODI proves correctness, truth, safety, alignment or successful action;
- an R0, IK_rel, later R-family, corridor or alert result is an action threshold;
- one universal Controller policy fits every domain;
- monitoring alone prevents drift, manipulation or harm;
- assistive interpretation supplies missing evidence or hidden intent;
- a visual simplification is a complete machine or governance object.

Production use requires domain-specific validation, data governance,
security, fairness review, accountable authority and appropriate human
oversight. This cumulative boundary changes no KSODI formula and creates no
Controller canon. It does not authorize software merge, deployment, threshold
choice, intervention, tag, GitHub Release or DOI.
